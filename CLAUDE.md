# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This workspace contains three sibling directories:

- `overlay-prototype/` — **Active workbench.** Vanilla-JS + Vite prototype that renders Chick-fil-A menu boards by overlaying dynamic price/calorie text on a background image. This is the shape the new prototype is taking per `OVERVIEW.md`.
- `ai-menuboard/` — Python FastAPI backend implementing an agentic pipeline that generates full Angular 18 codebases from a prompt + reference image. Inherited from another developer; **reference material**, not the active build path.
- `ai-menu-board-output/` — Storage-only git repo where `gitlab_publisher.py` pushes per-job artifacts from the Python pipeline.

`OVERVIEW.md` at the root describes the prototype goal. The current direction is the simpler runtime-overlay approach in `overlay-prototype/`, not the full Angular generator in `ai-menuboard/`.

## overlay-prototype (active)

Vite dev server + static JSON data + Node build step. No framework. **Build-time composition**: a Node script merges design slots + pricing into per-(store, screen) static HTML overlay fragments; the browser just stacks a bg image under a fetched overlay HTML. Naming mirrors the Angular shape the Python pipeline emits (`ManifestFetchService`, `DynamicViewComponent`, `src/assets/active.json`) so the eventual port is mostly file moves.

### Run it

```bash
cd overlay-prototype
npm install
npm run build:overlays         # regenerate overlay artifacts whenever data/ changes
npm run dev                    # Vite dev server on :5173
```

`build:overlays` must run at least once before `dev` (the frontend fetches `/assets/active.json`, which is a build output).

### Data lifecycle (important)

Two independent update cadences, never share a file:

- **Designs** — rare, generated by analyzing menu-board PNGs via `scripts/figma-gemini-batch.js`. Each design is a self-contained artifact: background image path + flat list of text slots with positions and a catalog `tag` per slot.
- **Pricing** — frequent, per-store. Real POS feed delivered as XML (`data/pricing/{storeId}.xml`). Independent of designs; overwriting a pricing file does not require re-extracting any design.

`scripts/build.js` composes both inputs into two independent output streams per (store, screen):
- **Background image** — shared across all stores using that design. Changes only when the Figma sync runs. CDN-cacheable essentially forever.
- **Overlay HTML** — ~1–5KB fragment with absolutely-positioned `<div>` elements. Regenerates when that store's pricing or design changes.

Splitting them lets a pricing update invalidate only the tiny overlay file, not the heavy bg image. This is the whole point of build-time composition.

The frontend is dumb — it fetches `active.json`, stacks the two layers, done. It has no awareness of slots, fields, or the pricing schema. Those concerns live exclusively in `scripts/build.js`.

### Schema

**Catalog** (`data/cfa-items.json`) — authoring input. Flat dictionary keyed by a unique tag string. Each entry already encodes the item-and-variant combination as a single entity (variants are baked into the `menu-item` text):
```json
{
  "HONEY_PEP_PIM_CFA_MEAL": {
    "menu-item": "Honey Pepper Pimento CFA Filet Meal",
    "pricing-tag": 1007254,
    "group": "Summer Campaign 2026"
  }
}
```

The outer key (e.g. `HONEY_PEP_PIM_CFA_MEAL`) is the canonical id used everywhere downstream. It matches `<Tag>` in the pricing XML directly.

**Design** (`data/output/design-*.json`) — Gemini output, build-script input:
```json
{
  "id": "design-a",
  "backgroundImage": "/assets/design-a.png",
  "slots": [
    { "tag": "HONEY_PEP_PIM_CFA_MEAL", "field": "price",    "x": 268, "y": 540, "confidence": 0.94, "reasoning": "…" },
    { "tag": "HONEY_PEP_PIM_CFA_MEAL", "field": "calories", "x": 336, "y": 540, "confidence": 0.92, "reasoning": "…" }
  ]
}
```

Each slot is independent — `{tag, field, x, y, confidence, reasoning}`. `field` is `price` | `calories` (extensible: `promo_tag`, `allergen_note`, etc.). Coordinates are pixels in a 1920×1080 menu frame, anchored at the top-left of the rendered text. The renderer applies fixed font sizing/styling per `field` — text does not scale with the bounding box; only the start position comes from the slot. A slot renders exactly one text block.

**Pricing** (`data/pricing/store-*.xml`) — authoring input. Real POS feed; flat list of `<Item>` records:
```xml
<Items>
  <Item>
    <ItemId>1007254</ItemId>
    <Price>13.49</Price>
    <Tag>HONEY_PEP_PIM_CFA_MEAL</Tag>
    <Name>Honey Pepper Pimento CFA Filet Meal</Name>
    <Calories>1050</Calories>
    <CaloriesHigh/>
    <CaloriesLow/>
  </Item>
</Items>
```

`build.js` parses the XML into a `Map<tag, {price, calories}>`. Items without a `<Tag>` are ignored. Calories rendering: prefer `<Calories>` if non-empty; otherwise emit `<CaloriesLow>/<CaloriesHigh>` (e.g. `200/400 cal`); else fall back to `—` with a `.missing` class on the slot. A design referencing a tag the store doesn't carry shows `—` for that one slot only.

**Variants** (`data/variants.js`) — array of variant labels (`meal`, `entree`, `meal-8ct`, `1ct`, `m`, `chocolate`, `toppings`, …). **Detection-time hint only** — passed to Gemini's prompt to help it group prices/calories by proximity to variant labels, then collapse each (item, variant) pair into a single catalog `tag`. Variants do **not** appear in slot output or in the pricing schema.

**Registry** (`data/registry.json`) — authoring input:
```json
{
  "stores": {
    "store-001": {
      "name": "Atlanta - Peachtree",
      "screens": { "01": "design-a", "02": "design-b", "03": "design-c" }
    }
  }
}
```

The inline `screens` map is a prototype shortcut. Production will introduce a middle `layouts` tier (~5–10 named layouts shared across ~500 stores, each with screen count + design assignments). Extracting this is a one-file change: stores reference `layoutId`, a new `layouts.json` holds the mappings. The build script and frontend paths don't change.

**Manifest** (`public/assets/active.json`) — build output, runtime-fetched:
```json
{
  "generatedAt": "2026-04-16T...",
  "stores": {
    "store-001": {
      "name": "Atlanta - Peachtree",
      "screens": {
        "01": {
          "designId": "design-a",
          "background": "/assets/test-bg.png",
          "overlay": "/overlays/store-001-01.html"
        }
      }
    }
  }
}
```

Mirrors the role of `src/assets/active.json` in the Python prototype's generated Angular app (fetched at startup by `ManifestFetchService`), but carries artifact pointers instead of menu content — because our prototype does build-time composition and theirs does not.

### Slot extraction (current pipeline)

`scripts/figma-gemini-batch.js` is the active extractor. It bypasses the Figma MCP entirely and feeds Gemini local PNGs. This was a deliberate simplification — the earlier MCP-based scripts (`figma-claude.js`, `figma-gemini.js`) had silent tool-call failures that caused Gemini to hallucinate items and coordinates. Sending the rasterized PNG inline removes the MCP failure surface so detection accuracy can be evaluated cleanly.

How it works:
1. Loops over every PNG in `data/menus/full/`. Each filename (without extension) is treated as the `designId`.
2. Sends the image as inline base64 to Gemini along with:
   - A compact `{tag → menu-item}` catalog derived from `data/cfa-items.json`.
   - The variant vocabulary from `data/variants.js` as a detection hint for grouping item-name + variant label into a single entity.
3. Gemini returns structured JSON: one object per visible price/calorie value with `{tag, field, box_2d, confidence, reasoning}`. The model is instructed to skip — not invent — when no catalog tag is a reasonable match for an entity.
4. Converts each `box_2d` (normalized 0–1000) to pixel space and takes the top-left as the slot's `(x, y)` anchor. Writes the result to `data/output/{designId}.json`, ready for `npm run build:overlays`.

Run via `npm run figma:batch`. Required env: `GEMINI_API_KEY` (and optional `MODEL_NAME`, defaults to `gemini-3-flash-preview`). `figma-gemini-debug.js` runs the same pipeline on a single design and additionally writes a debug HTML overlay showing every bounding box on top of the source image — useful when investigating extraction errors.

### What's next to wire

- **Figma export automation** — `data/menus/full/*.png` is currently exported manually from Figma. Either re-introduce an MCP fetch step (now that the rest of the pipeline is debuggable) or use the Figma REST API to render nodes to PNG.
- **Right-anchor / center-anchor support** — the renderer treats slot `(x, y)` as a top-left CSS anchor. Right-aligned price text in the design will visually drift unless either the box's `xmax` is used or the renderer learns a per-slot/per-field anchor mode.
- **Multi-store wiring** — registry currently holds one store. Drop additional `data/pricing/{storeId}.xml` files in and add entries to `registry.json` to scale up.
- **Layouts tier** — add when the schema's inline screen-map shows strain, not before.
- **Angular port** — direct mapping: `src/services/manifest-fetch.js` → `src/app/core/services/manifest-fetch.service.ts`, `src/views/dynamic-view.js` → `src/app/features/menu/dynamic-view/dynamic-view.component.ts`, `public/assets/active.json` → `src/assets/active.json`. The build step (`scripts/build.js`) survives unchanged; it produces artifacts Angular consumes the same way vanilla JS does.
